# AMS API integration

The approved frontend layout and styling are retained. Screens now read server records, show empty/error states, and wait for server confirmation before reporting a successful save. Demo collections and local business-record persistence have been removed.

## Local setup

1. Run `unified-college-backend` using its existing environment and database configuration. The expected origin is `http://localhost:5000`.
2. In this frontend, copy `.env.example` to `.env.local` if an override is needed. `VITE_BACKEND_BASE_URL` accepts the backend origin; `/api` is appended by the client.
3. Run `npm run dev` in this frontend and sign in with an existing active AMS administrator account.
4. Optional: configure `VITE_PUBLIC_APPLICATION_URL` with the existing public overseas application website to enable copying its URL.
5. As in the old AMS, the college must exist in the database before use. For a fresh database, run `npm run setup:college` in the backend terminal and enter the real details. The command uses the existing college model and refuses to replace an existing record. Refresh College afterward; its existing edit form handles later changes and logo uploads. There is no Add College button.

Deploy the backend changes together with this frontend. New authenticated adapters provide dashboard summaries, finance reports, student summaries, profile/permission updates, bulk-upload previews, and receipt PDFs. Existing AMS endpoints continue to handle the underlying admissions and payment operations. File uploads use the backend's existing storage configuration.

## Connected areas

- Authentication, administrator identity, profiles, permissions, activity, notifications and calendar events.
- College, institutes, courses, requirements, fee schemes, categories, intakes, agents, representatives and commissions.
- Students across International, Domestic and Overseas types, editing, photos, document links, contract flags and overseas requests.
- Payments, settlement history, commission splits, ancillary fees, persisted receipt downloads and statement exports.
- Dashboard, reports, partner financial data, global search and CSV/XLSX bulk uploads.

## Existing form limitations

- New installment enrollments require a schedule, installment count and due dates. The approved form does not collect these, so the integration rejects this selection with an explanation rather than inventing a schedule. Existing installment data is retained when editing records.
- The progressive-course modal only selects a course type. The backend upgrade workflow also requires a target course and fee scheme. The modal explains the missing information and directs users to Edit Student; no upgrade success is simulated.
- Legacy `.xls` bulk uploads must be converted to `.xlsx` or CSV.
- Contract generation follows the existing backend's persisted document-generation flags. It does not add a new contract PDF rendering service.

## Performance review — 21 November 2026

The authenticated `/payment` screen was opened against the running local backend. Search, the status dropdown and the empty state were checked. There were no eligible payment rows, so real multi-page navigation and large-data responsiveness were not measured. No admissions, payments or account statuses were changed. Browser timing instrumentation was unavailable in the inspection runtime; no FPS or latency improvement is claimed.

Changes made:

- Main Payments table now requests only the displayed page, with debounced server search, filters, totals and stable sorting. It no longer downloads every page and the entire ledger on initial entry.
- Students registry now requests one page with server-side type, course, intake, status, enrollment month/year, country and search filters. Course/intake/year choices load independently of the current page. Local maps to the backend's Domestic type; nationality is no longer used to guess student type. Search includes the actual contract/student number, and course/document joins run after pagination when not required for filtering. Only projected registry fields and the current page's signed photo URLs are returned.
- Student row links use the database ID directly, avoiding a full registry download to resolve a human-readable student number. Add/delete and bulk-upload completion refresh the current page and options. A compound type/date/ID index supports the standard sorted view; verify its query plan against production-sized data before claiming a latency improvement.
- Individual ledgers are fetched only when opened and restricted to that payment ID. Settlement detail also requests scoped history.
- Full Payment History now pages the transaction log directly, with independent real payment-method choices, server search/status filters, totals and a stable date/ID sort. It no longer fetches all payment pages or loads full payment documents just to display transactions. Search can match receipt/application/ancillary receipt numbers, transaction reference, student number/name, college and course. Normal page loads join display fields only after the page limit. Historical log rows remain visible even when a linked student/payment record is missing.
- History receipt actions now download the actual log's PDF instead of displaying a fake success toast. Inapplicable fee-type buttons and pending-transaction receipts are disabled. Receipt numbers open the associated payment detail, and student links use database IDs. Partial receipts marked `remaining` are treated as received transactions; refunds remain distinct. Unknown statuses default to Pending rather than claiming payment success.
- Course filter choices come from a small independent options endpoint, rather than only the visible page.
- Export now downloads an actual CSV. Full matching data is fetched in batches only after the user clicks Export.
- Collection mutations no longer immediately reload the same component twice through their own update event.
- Shared dashboard section entrance duration is 180ms instead of 500ms, with shorter staggering. Payments view transitions no longer animate blur. Layout, colors and typography are preserved.
- Dashboard totals, monthly enrollment, monthly sales/outstanding fees, program breakdowns, payment-status buckets and intake document counts now use MongoDB grouping. Orphan/deleted/upgraded student references remain excluded from dashboard payments and receipts; optional intake filtering applies consistently. Only compact buckets and at most 20 pending cards return to Node. Course/category totals use database counts/grouping rather than complete course records.
- Finance ledger joins, projected receipt rows and partner commission/volume/student-count calculations now run in MongoDB. Zero-activity partners remain in the output and existing formulas/response fields are preserved. The finance endpoint still returns all projected ledger rows and per-partner applications for its existing consumers; it is not yet a fully paginated report API.

Request lifecycle: opted-in authenticated JSON GETs reuse cloned responses for 10 seconds in memory (100-entry limit, never browser storage). Cache keys include session, normalized URL/filter params, timeout and TTL. Writes clear cached reads before starting and after completing; successful writes notify mounted useApiQuery views to reload, and manual reload bypasses cached responses. Old in-flight responses cannot repopulate an invalidated cache. Logout/token changes clear cached data and abort tracked queries. Downloads, custom-header/auth reads and errors are not cached; payment/CP exports explicitly bypass cached pages.

The paginated Students, Payments, History, finance ledger/partners/applications, CP reports and finance/filter options forward hook cancellation signals to fetch. Shared requests retain independent subscribers: leaving one view does not cancel another view’s identical request, while the last subscriber aborts transport. Timeout remains an error; ordinary cancellation does not display an error. Backend/MongoDB operations already started are not guaranteed to stop when fetch is cancelled. Remaining legacy loaders still have generation guards but may not forward signals.
